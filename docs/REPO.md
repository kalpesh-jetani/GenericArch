# Repository — versioning, local development, tooling choice

Reference for working across the single repo and its two extracted packages.

- **When to read this:** changing an extracted package, setting up a machine, or asking why the
  project isn't generated by Tuist.
- **Layout and the extraction test:** CLAUDE.md §4 — those are always-on rules. Everything below is
  reference.
- **Releasing an extracted package:** the `release-bump` skill.

---

## Versioning

| What | Versioned? | Mechanism |
|---|---|---|
| Packages under `Packages/` | **No** | Git history is the version. One commit changes a package and its consumers together |
| `GenericArch-NetworkKit` | Yes | Semver, tagged, own CI |
| `GenericArch-ImageCache` | Yes | Semver, tagged, own CI |
| The app | Yes, separately | Marketing version + build number — [DELIVERY.md](DELIVERY.md) |

Rules for the two extracted repos:

- Breaking a public API = **major**. Adding one = **minor**. Internal fix = patch.
- Consumers declare `.upToNextMajor(from: "1.2.0")`. **Never** `branch:` or `revision:`.
- `Package.resolved` is committed at this repo's root and is the record of what ships.
- Changing one is **two steps**: tag there → bump `Package.resolved` here. If a change needs a
  third, the boundary is wrong — see the `release-bump` skill for what each symptom means.

## Local development against an extracted package

```bash
swift package edit NetworkKit --path ../GenericArch-NetworkKit
# … work across both …
swift package unedit NetworkKit
```

Clone the two extracted repos beside this one:

```
parent/
├── GenericArch/                 ← this repo
├── GenericArch-NetworkKit/
└── GenericArch-ImageCache/
```

**Never commit a `.package(path:)` for those two** — it is a local override only, and a path
dependency that reaches a tag breaks resolution for everyone. For packages under `Packages/`, a path
dependency *is* the mechanism.

Before tagging or releasing, confirm no override is active:

```bash
swift package unedit --force NetworkKit ImageCache 2>/dev/null; swift package resolve
```

## Why SPM generates the project

**Chosen: SPM.** Packages carry their own manifests; the repo holds one thin `.xcodeproj`; no extra
toolchain to install, version, or upgrade.

**Rejected — do not re-propose without new information** (also in [DECISIONS.md](DECISIONS.md)):

| Option | Why not |
|---|---|
| **Tuist** | Better conflict-free project generation, but becomes a second build-system-of-record with its own upgrade treadmill |
| **XcodeGen** | Lighter than Tuist, but still a YAML source of truth to keep in sync, and carries unmaintained-risk |

**The revisit trigger:** the `.xcodeproj` starting to produce real merge conflicts. With a thin shell
it shouldn't — which is why [PROJECT.md](../.claude/notes/PROJECT.md) forbids build settings in the
Xcode UI. If conflicts start, say so rather than resolving the same one twice.

## Permissions (`.claude/settings.json`)

Allowlisted so they never prompt: **read-only inspection only** — `git status/diff/log/show`,
`grep`, `find`, `ls`, `swift package describe`, `detect-toolchain.sh`, the trigger test.

**Builds, tests and `check.sh` are deliberately *not* allowlisted.** CLAUDE.md §2.12 says Claude
never runs them unasked; the approval prompt is the mechanical backstop for that rule, and
allowlisting them would remove it. You run them — `/build` is the sanctioned path. Mutating git is
absent for the same reason (§2.11).

Add to the list only what you would let run unattended a hundred times.

## Adding a package

1. Create `Packages/<Name>/` with its own `Package.swift`,
   a `platforms:` line copied from a sibling package — the floors live in the manifests, not here.
2. Wire consumers with `.package(path:)`. Check the edge against CLAUDE.md §3's direction before
   adding it.
3. Add its `<Name>.md` and one row to `.claude/MAP.tsv`.
4. Link it in the app targets; record it in [PROJECT.md](../.claude/notes/PROJECT.md).
5. `swift test --package-path Packages/<Name>` must pass standalone.

Do **not** propose extracting it to a repo — CLAUDE.md §4.2 gates that, and a new package fails the
"actually reused" test by definition.
